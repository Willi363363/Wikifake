# Track F — quests

| | |
|---|---|
| **State** | 🔶 F.1 done |
| **Branch** | `feat/quests` |
| **Depends on** | track E |
| **Delivers** | daily and weekly quests, generated by rules, run by a cron |

## Objective

A reason to come back tomorrow, produced by a machine. Daily and weekly.
Monthly if the same engine gives it for free — and only then.

## The constraint that decides the design

The owner's requirement, in their words: *once the app is launched I want
nothing left to do, I will not have the motivation to add content every
month.* Taken literally, because taken literally it is a good constraint.

**So there is no content in a quest.** A quest is a rule applied to numbers
the game already records: *find 12 falsifications today*, *finish 5 games this
week*, *play a round without buying a hint*. The catalogue of rules is written
once; the quests are generated from it, seeded by the date, forever.

**And there are no seasons.** A season is a content calendar wearing a
mechanic's clothes. Refused explicitly — `11-deferred.md`.

## The shape

Three pieces, deliberately boring:

- **A rule catalogue** — in `packages/domain`, next to the scoring scale and
  the item catalogue, because it is the same kind of thing: a business rule
  that must exist in exactly one place. Each rule declares what it counts, its
  target range, its period and its reward.
- **A generator** — deterministic. Given a player, a period and a date, it
  produces the same quest set every time it runs. That determinism is what
  makes a missed cron harmless: rerun it, get the same answer.
- **A progress reader** — quest progress is derived from the events the game
  already writes. Nothing in the game loop needs to know quests exist.

That last point is the one to hold. **A quest must never be able to break a
round.** If the quest engine is down, the game is unaffected — the player just
sees no quests. Wiring quest writes into the round's hot path would trade the
game's reliability for a retention feature, and that is the wrong trade.

### F.1 — what the catalogue decided

**A rule may only count what a finished round already carries.** Checked against
the schema rather than assumed: `participant` holds `submitted_at`, `score`,
`true_positives`, `false_positives` and `hints_used`, and its `game` holds `mode`
and `total_fakes`. That constraint is what made the file short, and it ruled two
obvious quests out — **items used are not recorded anywhere** (`score_stolen` is
what was done *to* a player, not what they cast), and **a streak has no time
dimension**, so "a streak of three today" is unanswerable. Both are written down
in `quests.ts` so the step that wants them starts from a decision.

**A rule is a tally, a qualifier, a period, a range and a reward.** The tally is
what accumulates — rounds, falsifications found, or points — and the qualifier is
which finished rounds count: `any`, `perfect`, `noHints`, `nothingWronglyMarked`,
`multiplayer`.

**The qualifier is data and never a predicate.** E.4 already had to hand
`isPerfectRound` into `queries/stats.ts` as an argument, because *data does not
depend on rules* and `@wikifake/db` may not import `domain`. A qualifier
expressed as a function is one F.4 cannot turn into a `where` clause, so it would
force the progress reader to walk every round a player has ever played.

**`points` is the sum of each qualifying round's score floored at zero.** C2.3
lets a score be negative and does not clamp it, so an unfloored sum would hand a
player a quest whose progress goes *down* after a bad round. F.4 implements the
floor; F.1 chose it.

**The identifiers stay in `domain` until a quest crosses the wire.** `protocol`
holds the identifiers that are message contracts — that is what `items.ts` means
by it — and F.1 sends nothing anywhere. They become a `protocol` enum at F.7,
which is a re-export rather than a rename because nothing outside the package
reads them before then.

**The reward is a number of coins, and there is no wallet.** Track H owns the
balance; F.6 credits inside the transaction that marks a quest claimed. Until
then a reward is what a quest is worth. Daily to weekly is roughly one to four
and not one to seven: a weekly set that pays a week of dailies makes the dailies
pointless.

**`solo` was in the qualifier union and is not any more.** Nothing counted it —
every daily is completable alone already — and a dead member is a `case` F.4 must
write, a branch a test must cover, and a promise on the quests screen no rule
keeps. `quests.test.ts` holds that: every qualifier and every tally has a rule
using it.

### F.5 — The cron

A scheduled function. Two properties it must have, because both failures are
certain over a year of running unattended:

- **Idempotent.** Running twice for the same date changes nothing. The
  generator's determinism makes this free.
- **Self-healing.** A player whose set was never generated — new account,
  missed run, outage — gets it on their next request, not on the next cron.
  The cron is an optimisation; the read path is the guarantee.

### F.6 — Claiming exactly once

A reward is credited in the same transaction that marks the quest claimed, or
neither happens. This is where a retry gives a player unlimited coins, and it
is worth the test that proves it cannot.

## Exit gate

- A day passes with no human involvement and every player has a fresh set.
- The cron is run twice for the same date and nothing is duplicated.
- A player created at 03:00 sees quests immediately.
- The quest engine is stopped entirely and a full game still plays.
- Claiming twice, concurrently, credits once.
