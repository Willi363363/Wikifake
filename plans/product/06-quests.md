# Track F — quests

| | |
|---|---|
| **State** | ✅ done — nine steps, and the cron runs unattended |
| **Branch** | `feat/quests` |
| **Depends on** | track E |
| **Delivers** | daily and weekly quests, generated by rules, run by a cron |

## Objective

A reason to come back tomorrow, produced by a machine. Daily and weekly.
Monthly if the same engine gives it for free — and only then.

## The constraint that decides the design

The owner's requirement, in their words: *once the app is launched I want
nothing left to do, I will not have the motivation to add content every
month.* Taken literally, because taken literally it is a good constraint.

**So there is no content in a quest.** A quest is a rule applied to numbers
the game already records: *find 12 falsifications today*, *finish 5 games this
week*, *play a round without buying a hint*. The catalogue of rules is written
once; the quests are generated from it, seeded by the date, forever.

**And there are no seasons.** A season is a content calendar wearing a
mechanic's clothes. Refused explicitly — `11-deferred.md`.

## The shape

Three pieces, deliberately boring:

- **A rule catalogue** — in `packages/domain`, next to the scoring scale and
  the item catalogue, because it is the same kind of thing: a business rule
  that must exist in exactly one place. Each rule declares what it counts, its
  target range, its period and its reward.
- **A generator** — deterministic. Given a player, a period and a date, it
  produces the same quest set every time it runs. That determinism is what
  makes a missed cron harmless: rerun it, get the same answer.
- **A progress reader** — quest progress is derived from the events the game
  already writes. Nothing in the game loop needs to know quests exist.

That last point is the one to hold. **A quest must never be able to break a
round.** If the quest engine is down, the game is unaffected — the player just
sees no quests. Wiring quest writes into the round's hot path would trade the
game's reliability for a retention feature, and that is the wrong trade.

### F.5 — The cron

A scheduled function. Two properties it must have, because both failures are
certain over a year of running unattended:

- **Idempotent.** Running twice for the same date changes nothing. The
  generator's determinism makes this free.
- **Self-healing.** A player whose set was never generated — new account,
  missed run, outage — gets it on their next request, not on the next cron.
  The cron is an optimisation; the read path is the guarantee.

### F.6 — Claiming exactly once

A reward is credited in the same transaction that marks the quest claimed, or
neither happens. This is where a retry gives a player unlimited coins, and it
is worth the test that proves it cannot.

### F.8 — Breadth, from the catalogue the unions already described

**The generator draws 3 of 5 daily and 2 of 5 weekly**, so a player saw one of
ten possible sets. F.1 wrote five rules per period and the two unions allow
fifteen combinations per period; the ten that were missing were missing because
nobody had written the row, not because anything refused them.

```
C(5,3) = 10 daily sets        C(8,3) = 56
C(5,2) = 10 weekly sets   →   C(8,2) = 28
```

**Six rows, and no new mechanism.** `progressFor` filters by qualifier and then
switches on tally — the two are orthogonal by construction, which is what F.1
bought by making the qualifier data rather than a predicate. So every pair below
was already computable the day F.4 shipped.

| Rule | tally × qualifier |
|---|---|
| `DAILY_PERFECT_ROUND` | rounds × perfect |
| `DAILY_UNAIDED_FALSIFICATIONS` | falsificationsFound × noHints |
| `DAILY_CLEAN_POINTS` | points × nothingWronglyMarked |
| `WEEKLY_UNAIDED_ROUNDS` | rounds × noHints |
| `WEEKLY_CLEAN_ROUNDS` | rounds × nothingWronglyMarked |
| `WEEKLY_PERFECT_POINTS` | points × perfect |

**No daily multiplayer rule**, and that is the one pair deliberately left
unwritten. F.1's reason stands: a daily quest a player cannot finish alone is a
daily quest that expires.

**The targets keep the shape the test holds.** `quests.test.ts` requires the
cheapest week to ask more than the cheapest day, per tally — so a daily rule
lowering its tally's floor moves what a weekly rule must clear. Both floors
moved here: falsifications to 4 and points to 250 on the daily side.

**The copy had no guard, and adding six rules is when that costs something.**
`screen.tsx` reads `rules.${quest.ruleId}` — a key composed at runtime, so a rule
without a message is a quest that renders its own identifier to a player, and no
build and no test said so. `catalogue.check.ts` holds French to English and
neither to the catalogue. `quests.test.ts` in `apps/web` now holds all three.

### F.9 — Two tallies the schema already carried

F.8 crossed the unions it was given. This one adds to them, and only where a
column already answers — F.1's constraint, unchanged.

**`distinctArticles` counts `game.source_url`.** It is the one tally that is not
a sum: two rounds on the same page are one article, so the quest cannot be
finished by replaying a favourite. `topic` would also have worked —
`article/src/source.ts` sets it to *the resolved page title, not what the player
typed* — but a URL is one page by construction where a title is one page by
convention. (`admin-content.ts` still describes `topic` as what a player typed.
That comment is stale; it is not this step's to fix.)

**`itemsCast` is weekly-only**, and that is F.1's multiplayer argument rather
than a gap. `with_items` belongs to `room`, and a solo game has no room, so a
cast is something only a room affords. A daily quest asking for one would expire
for anybody playing alone.

**The count is a correlated subquery, not a join.** Joining `item_use` would
multiply the participant row once per item and carry every other figure with it —
a score counted three times for three casts. TypeScript cannot see that failure,
so it has a case against a real Postgres instead.

**One test was refined rather than extended, and it is worth saying which.**
`quests.test.ts` asserted *the cheapest week asks more than the cheapest day* for
every tally, over a list spelled out by hand. That held for three tallies and was
never a rule anybody stated. `itemsCast` has no daily side, so the list is now
two — the tallies at both periods, and the weekly-only ones — with a third case
asserting that every tally in the catalogue appears in exactly one of them. The
assertion is stronger than before: a tally nobody decided about now fails.

## Exit gate

Four of the five are proved by tests named in the sheets. **The first could not
be, from here:** the schedule is declared in `vercel.json`, and Vercel sends the
bearer token only if `CRON_SECRET` exists in the project's environment.

**It was set on 2026-09-11**, and the endpoint says so from outside: with no
token it answers **401** — configured and refusing — where it answered 503 while
unconfigured. The two codes were chosen to be told apart in a log for exactly
this moment, and the distinction is the whole evidence that the variable
arrived. The step was ✅ before that, and correctly: F.5 made the read path the
guarantee, so every player had quests the whole time the cron did not run. What
was missing was the *unattended* half, and it is the half that matters over a
year.

- A day passes with no human involvement and every player has a fresh set.
- The cron is run twice for the same date and nothing is duplicated.
- A player created at 03:00 sees quests immediately.
- The quest engine is stopped entirely and a full game still plays.
- Claiming twice, concurrently, credits once.
